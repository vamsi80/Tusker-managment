Project-level settings
Context
The workspace already has one configurable-permissions system: a static role→capability matrix in capabilities.ts, narrowed by permissionOverrides JSON on Workspace and WorkspaceMember, resolved by resolveCapabilities, edited in Settings → Permissions.

Nothing equivalent exists at the project level. Grepping settings|config|preferences against schema.prisma returns zero matches — Project has no config column, no toggle, no settings relation. Every behaviour inside a project is either governed by workspace-wide rules or hard-coded in the service layer. A workspace running three verticals (White Tusker / Lattice Lane / Miscellaneous) cannot make one project stricter than another.

This adds a Project Settings page inside the project route, covering per-project permission narrowing and per-project behaviour.

Design
Storage — two JSON columns, mirroring the existing precedent
model Project {
settings Json? // sparse behaviour deltas; NULL = every default
permissionOverrides Json? // { "MEMBER": { "task:status": false }, ... } keyed by ProjectRole
}
One additive migration, both nullable, no backfill — same as 20260825120000_add_permission_overrides. Sparse deltas mean a project that has never been configured stores nothing and behaves exactly as today.

Migration warning: this database connects with search_path = boq, public, extensions. ADD COLUMN ... JSONB is safe, but any CREATE TYPE must be written CREATE TYPE public."Foo" or it lands in boq and Prisma writes fail with 42704.

Resolution — one new module mirroring capabilities.ts
src/lib/constants/project-settings.ts, deliberately copying the shape of capabilities.ts: no server-only, so the settings UI can preview resolution live, and the same junk-tolerant coercers so malformed JSON degrades to {} instead of throwing.

Delivery to the UI — no new fetch
ProjectService.getProjectLayoutData (project.service.ts:644-654) already returns { members, permissions } and is mounted around every project page by ProjectLayoutProvider. Add settings to that payload; every component reads it from useProjectLayout().

The page
src/app/w/[workspaceId]/p/[slug]/settings/page.tsx + loading.tsx, following the shape of every sibling view (list/page.tsx:25-29).
Entry: a gear icon pinned right in project-nav.tsx:128-138, not a seventh tab — six already overflow-scroll.
Permission grid: copy permissions-manager.tsx — per-checkbox server action, optimistic with rollback, and its trick of sending value: null to clear an override when a toggle returns to its default.
Behaviour cards: one form + Save per card, following attendance-settings.tsx's hasChanges diff and single bulk PATCH.
API
GET / PATCH /:projectId/settings in hono/routes/projects.ts, next to the existing PATCH /:projectId and GET /:projectId/permissions. Zod at the boundary; guard reuses permissions.isWorkspaceAdmin || isProjectAdmin(...). On write, recordActivity({ broadcastEvent: "team_update" }) so other users don't run stale — the workspace permissions action omits this and that's a bug not to copy.

Riskiest stage, and the reason it is last: F1/F2 change an approval chain that authorises money, involved-users.ts is shared by every task event, and G1 means adding an archived filter to every project query — getWorkspaceProjects, getMinimalWorkspaceProjects, the sidebar, layout data — or archived projects keep showing up.

Two traps this must not step in

1. The workflow rules exist in two copies. Server: tasks.service.ts:1786-1954. Client: isTransitionAllowed / isCommentRequired at subtask-status-changer.tsx:92-149. Every Stage 2 setting must feed both, or the UI offers moves the server rejects. The lazy fix is to export one predicate from project-settings.ts and call it from both sides, deleting the client duplicate.

2. Two permission resolvers disagree. getUserPermissions deliberately does not let a workspace admin imply PM/Lead; ProjectService.getPermissions (project.service.ts:607) does. Hono task routes use the first, the project layout context uses the second. Settle this in Stage 0 or a setting will appear to work in the UI and not on the API.

Related dead weight worth deleting while in here: project-access.ts exports a whole permission matrix of which only isProjectAdmin is imported, and project-header.tsx is an unimported duplicate header that wouldn't typecheck if it were used.
