Reward points system
Context
There is no points, score, rewards or gamification feature anywhere in this codebase — this is greenfield. The goal: completing a task early earns the assignee points equal to the working days it was early, on time earns nothing, late deducts the working days it was late. Owners, admins and managers can also award or deduct points by hand for things unrelated to tasks.

Two facts from the existing code shape everything below.

Task has no completion timestamp. There is no completedAt or closedAt column (schema.prisma:349-398). updatedAt is clobbered by any later edit, so today the only durable record of when something finished is the Activity row written inside the status transaction. Early/late maths needs a real timestamp.

There is a live data-corruption bug in the completion counter. tasks.service.ts:2332 passes isNowCompleted as data.status === "COMPLETED". When data.status is undefined — renaming a completed task, editing its description, changing its tags — that is false while wasCompleted is true, so the wasCompleted && !isNowCompleted branch at task.repository.ts:153 fires and decrements the parent's completedSubtaskCount on an edit that changed no status at all.

Measured against the live database: 9 of 180 parent tasks have a wrong completedSubtaskCount, and all 9 are under-counted — never over-counted, which is precisely this bug's signature. Progress bars are understating real progress right now. With a points hook on that same guard, every typo fix on a completed task would also silently reverse someone's points. This gets fixed before anything else is built.

Decisions taken
Who earns The assignee at the moment of completion
Working day Anything that is not a Sunday and not a public_holiday for that workspace. Saturday counts as a working day — this matches attendance.service.ts:785, which treats Sunday as the only weekly off
No dueDate Score nothing, write no row
Re-open Writes a compensating entry and stamps the original; re-completing scores fresh against the new date. Close/reopen cannot farm points
Manual awards Owner / admin / manager, written reason mandatory
Period Configurable from the team settings page: reset period, and display window
Visibility — deferred by design. You are adding new manager-level logic to the workspace, so the scope rule is isolated in one function (PointsService.visibleMemberIds) rather than spread across queries. The interim rule it implements: owners and admins see everyone; managers see their reports but not themselves; members see only their own total. When the new manager model lands, that one function changes and nothing else does. Note this deliberately diverges from the existing precedent at attendance.service.ts:426, where a manager's scope includes themselves.

Architecture
An append-only ledger. A balance is SUM(points) over a window; rows are never edited or deleted. Reversal writes a compensating row rather than removing the original, so "why did my points drop" is always answerable from the data.

The award joins the status-change transaction. Two service methods can write COMPLETED — updateSubTaskStatus → TaskRepository.updateStatus, and updateTask → TaskRepository.updateTaskAndParentCount — and both already receive wasCompleted / isNowCompleted and branch on them. Those two guards are the only completion choke point in the system. Hooking there means the points write commits or rolls back with the status change. The alternatives are both unsafe: TaskEvents.onStatusChanged is fire-and-forget (broadcast in a detached IIFE, invalidation .catch()-ed) and is never called by updateTask at all; recordActivity buffers in a module-level array flushed every 5s and loses entries on crash.

All I/O stays out of the transaction. The holiday lookup and the assigneeId → workspaceMemberId resolution happen in the service, before $transaction opens. The repository receives a finished award payload and only writes — preserving that file's existing "no business logic" contract.

Schema
/// Append-only reward ledger. Balance = SUM(points) over a window. Rows are
/// never edited or deleted: re-opening a completed task writes a compensating
/// row, so close/reopen cannot farm points.
/// NOTE: a partial unique index (taskId WHERE kind='TASK_COMPLETION' AND
/// reversedAt IS NULL) exists in migration 20260913090000. Prisma cannot
/// express it — never `prisma db push` this model or it is silently dropped.
model PointsEntry {
id String @id @default(uuid())
workspaceId String
workspaceMemberId String
points Int
kind String // TASK_COMPLETION | TASK_REVERSAL | MANUAL
reason String
taskId String?
reversedAt DateTime?
reversesEntryId String?
awardedById String? // null for automatic awards
occurredAt DateTime @default(now())
createdAt DateTime @default(now())
// relations + @@index([workspaceId, occurredAt desc]),
// @@index([workspaceMemberId, occurredAt desc]), @@index([taskId])
}
Plus Task.completedAt DateTime?, and two scalar columns on Workspace: pointsResetPeriod String @default("MONTHLY") and pointsDisplayPeriod String @default("CURRENT").

Why workspaceMemberId and not projectMemberId (one human has many — every balance becomes a join and group-by, and history fragments when they leave a project) or userId (loses workspace scope, and the reset period is per-workspace). It is also the row the team page already iterates, and since the deactivation work it is never hard-deleted, so the ledger cannot be orphaned.

FK rules matter here. taskId is SET NULL — mirroring Task.assigneeId, never createdById. A RESTRICT would make deleting any scored task throw a raw FK error, which is exactly the class of bug the deactivation migration was written to eliminate; a CASCADE would delete earned points when a task is tidied away, which an append-only ledger must never do. awardedById is SET NULL so a departing awarder doesn't erase awards. workspaceMemberId and workspaceId cascade.

kind is TEXT, not an enum. This database connects with search_path = boq, public, so an unqualified CREATE TYPE lands in boq while tables sit in public and every write then fails with 42704. That has already bitten this repo twice (20260904120000_add_project_category and its fix migration). notification.type is a plain String for the same reason.

Two scalar columns, not Workspace.settings Json. Project has a JSON settings column so coerceProjectSettings is right there; Workspace has a dozen scalar settings columns and no JSON at all. Scalars are both the local convention and the smaller diff.

Settings columns need no new endpoint. WorkspaceService.updateSettings (workspace.service.ts:1927) already exists, is already OWNER/ADMIN-gated and already has an allow-list — add the two field names there and to the getSettings projection. Mobile gets it free.

Working-days utility
Goes in date-utils.ts, which already owns getISTDateOnly, addOneDayUTC, calendarDayKey and the @db.Date conventions. There is no existing business-day helper anywhere — this is the first.

/\*\* Signed working days between two IST calendar days. Positive = `to` is later.

- Holidays are passed in, never queried here, so a bulk caller loads once. \*/
  export function signedWorkingDays(from: Date, to: Date, holidayKeys: Set<string>): number
  Half-open on the earlier end, so same day = 0 and the next working day = 1. Worked examples:

Due Completed Result Why
Fri Thu +1 one working day early
Mon Sat +1 Sunday skipped
Fri Mon −2 Sat + Mon, Sunday skipped
any same day 0 and no row is written
The IST frame is the trap. dueDate is stored as an IST-midnight instant (18:30Z the day before) via parseIST, so reading its UTC parts raw is an off-by-one. public_holiday.date is @db.Date, already UTC-midnight, so it lines up with no conversion. completedAt is a real instant and genuinely needs projecting — a task completed at 02:00 IST is 20:30Z the previous day. Everything goes through getISTDateOnly first.

Holidays load with one indexed range query over the existing @@unique([workspaceId, date]) — not a per-task scan, not a cache.

Implementation order

1. Fix the counter bug — alone, first. At tasks.service.ts:2332:

const isNowCompleted = updateData.status !== undefined
? updateData.status === "COMPLETED"
: task.status === "COMPLETED";
Then a one-off recount for the 9 corrupted parents. Verify: rename a completed subtask and confirm the parent's count holds; re-run the drift query and get 0 rows. This is a shippable bug fix on its own and is worth landing even if the rest is postponed.

2. Migration + schema + generate. House style: prose comment, idempotent DDL, schema-qualified, no CREATE TYPE. Verify: migrate on a scratch DB, confirm the partial index with \d+, then do a write through Prisma — that is what catches the 42704 class of failure, not a raw SQL insert.

3. signedWorkingDays + periodStart — pure functions, no DB. Verify: a unit test beside the existing calendar-day-key.test.ts covering the four cases above, a holiday inside the span, and the IST boundary (completed 02:00 IST on the due date scores 0, not −1). This is the one place a wrong answer is invisible in the UI, so it gets the test.

4. PointsService (packages/core/src/server/services/points/, following the member-todo shape): holidayKeys, computeAward, awardManual, summary, entries, visibleMemberIds.

5. The repository hook. Collapse the duplicated three-branch guard in updateStatus (L261) and updateTaskAndParentCount (L147) into one private helper called from both — a hook added to only one is how the second path silently stops scoring. It stamps completedAt under the same guard, so timestamp and ledger can never disagree. Reversal reads the open award inside the transaction. Verify end to end: task due tomorrow → REVIEW → COMPLETED gives one +1 row and a non-null completedAt; back to IN_PROGRESS gives reversedAt set, a −1 row, completedAt null, net 0; re-complete scores fresh. A task with no dueDate produces zero rows.

6. Capability + manual award route. Add { id: "points:award", label: "Award or deduct points", group: "Points" } to capabilities.ts — it flows into the permissions grid and the zod enum automatically. The easy thing to get wrong: DEFAULT_CAPABILITIES is all(true) minus exceptions, so MEMBER, VIEWER, PROCUREMENT and ACCOUNTS each need an explicit "points:award": false or every viewer can award themselves. OWNER/ADMIN/MANAGER keep all(true), which is exactly the set you asked for — and is why this is a capability rather than isWorkspaceAdmin, which excludes MANAGER. Route POST /api/v1/points/:workspaceId/awards, gated per-handler not by router middleware, because reads on the same router must stay open. Validation: non-zero integer, |points| ≤ 1000 (fat-finger guard, not a business cap), reason 3–500 chars mandatory, target an active member of this workspace, and self-award blocked. Notifies the recipient with the reason — someone losing points must be told why.

7. Read API + visibility. GET /points/:workspaceId/summary and /entries, both scoped through visibleMemberIds. Reversals render as their own line rather than hiding the original.

8. api-client + settings UI. packages/api-client/src/points.ts mirroring workspacesClient. Settings tab at team/settings/page.tsx beside Attendance and Leaves — that page already gates on admin and already loads the workspace settings row, so the two fields arrive with no new fetch.

Not doing, and why
No retroactive backfill. There is no truthful completion date for historical tasks: completedAt is brand new and updatedAt often just means "when someone last retagged this". Scoring people against that would put unappealable numbers on real performance records — the evidence to dispute them does not exist. Everyone starting at zero is fair in the only way that matters: identically.

Also skipped for now: realtime broadcast on award, a holiday cache, per-project scoping, and reversal of manual awards (cancel by writing an opposite entry).

Open question
pointsResetPeriod and pointsDisplayPeriod overlap — the first sets where the balance window starts, the second how far back the history list goes, and CURRENT makes the second defer to the first. Worth confirming you want two knobs rather than one before I build two selects.
